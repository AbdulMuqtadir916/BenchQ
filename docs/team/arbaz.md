# Arbaz — Standalone BenchQ Apply Chrome Extension

## Overview

Manifest V3 Chrome extension with a React/TypeScript Side Panel. For the signed-in BDE it displays saved applications (the backend representation of a candidate/job favorite), opens the job's stored URL in a new tab, and marks a saved application as `applied` in BenchQ. It never submits a form to an employer.

All extension implementation is isolated in `extension/`, alongside the root `package.json` scripts for `ext:build` and `ext:watch`. Two root settings leave the extension's tooling out of the app's checks: `tsconfig.json` excludes `extension/vite.config.ts` and `eslint.config.mjs` ignores `extension/dist/`.

## Structure and technology

```text
extension/
├── public/manifest.json       MV3 side panel and service worker registration
├── src/
│   ├── api.ts                 Session, saved applications, résumé answers and files, and status API calls
│   ├── autofill/              Matching, never-fill rules, tab bridge, and the review panel
│   ├── background.ts          Opens the panel; keeps each tab's job connection
│   ├── engine/                The autofill engine: see its README for sources and licences
│   ├── chrome.d.ts            Minimal Chrome API declarations
│   ├── JobTabs.tsx            The Saved and Applied tabs
│   ├── main.tsx               Side panel UI and session/job state
│   ├── page/                  Injected page script: scans, fills, verifies and undoes
│   ├── style.css              Tailwind setup: the website's tokens, type scale and buttons
│   └── ui.ts                  Tailwind class lists the panel's components share
├── index.html
├── package.json
├── package-lock.json
├── postcss.config.mjs         Tailwind, the same way the website loads it
├── tsconfig.json
└── vite.config.ts
```

Uses React, TypeScript, Vite, Tailwind v4 (through PostCSS, as the website does), and Chrome Side Panel API. Tailwind's reset only reaches the side panel: nothing is injected into employer pages. Vite outputs to `extension/dist/`; the checked build produced `manifest.json`, `index.html`, `panel.js`, `background.js`, and CSS under `assets/`.

## Reused BenchQ behavior

- **Login and session:** the existing sign-in page is `/{firm}/sign-in` by route group resolution at `/sign-in`; the extension opens `${BENCHQ_URL}/sign-in` in a new tab. It does not render a login form or access HttpOnly cookies. Authenticated `fetch` calls use `credentials: "include"` and `/api/auth/me`, whose response contains `principal`, `user`, and `firm`.
- **Session after login/logout:** after Login is clicked, the open panel polls `/api/auth/me` every 2.5 seconds for up to two minutes; when the cookie session is available it reloads the candidate list and jobs. While signed in, it checks the session every 15 seconds and when the panel regains focus or visibility. A 401 clears the panel data and returns to sign-in; transient network errors leave the current session view intact. Refresh and retry controls are also provided.
- **BDE identification and isolation:** the extension requires `principal.kind === "firm"` and `principal.role === "BDE"`. It gets the BDE's candidate choices from `GET /api/firms/{firm_id}/candidates`, which the backend scopes to that BDE. The selected candidate ID is sent to the saved and applied application reads; the backend verifies candidate visibility again. References: `backend/api/routes_applications.py`, `backend/api/routes_candidates.py`, `backend/models/candidates.py` (`FavoriteJob` and `CandidateJob`), and `backend/models/db.py` (`Application`, `Job`).
- **Saved/favorite data:** in the candidate workflow, a saved application is the candidate/job favorite. `POST /api/applications` creates both the `FavoriteJob` and `Application(status="saved")`; it requires the job to be linked to that candidate. The extension lists these saved applications. The general Job Explorer's `JobMark` saved state remains a separate per-user frontend mock and is not what the candidate-scoped application endpoint reads.
- **Apply and applied state:** each saved job's stored URL opens the employer's posting. The `Apply` action calls `PATCH /api/applications/{id}/candidate-status` with status `applied`, the current revision, and a unique command id. Backend tracking removes the favorite when status moves away from `saved`. Separate Saved and Applied tabs show counts; applying moves the item to the Applied tab and disables its action. Saved-to-applied history is reloaded from the API after refresh.
- **Non-BDE:** displays the requested BDE-only explanation and no jobs.
- **Theme and identity:** the panel has an interactive Light/Dark toggle with the same Moon/Sun icon states as `src/components/theme/theme-toggle.tsx`; it remembers the selection in extension-local storage and uses BenchQ light and navy dark palette values. The signed-in header shows the user's name, BDE role, and firm.

## Autofill

- **Connection:** **Open job** opens the URL from the background worker and stores `tabId → application, candidate, job summary` in `chrome.storage.session`, ids only. Marking a job applied ends its connection on every tab, and the tab stays open. A tab the employer's page opens inherits it. Clicking a job's title does the same as **Open job**. While a job is linked the panel shows only that job, with no list or tabs, and the candidate dropdown follows it and stays locked; the ✕ on the card ends the connection and the tab stays open. Typing an address into the tab or closing it clears the connection.
- **Scan:** `page.js` is injected only into connected tabs, in all frames, on load, on a single-page route change, and when the regular check finds the form has changed. It reads and never writes. A captcha's frames (hCaptcha, reCAPTCHA, Turnstile, Arkose) are skipped: their controls, like hCaptcha's language menu, aren't part of the form.
- **Source:** the résumé picked in the **Resume** section: `GET …/candidates/{cid}/resumes/{rid}?autofill=true` sends that version's answers, checked against the caller's scope, in the format below. The panel holds them in memory and does all the matching itself: by each answer's `key` first, then by wording, by what a question asks for, and from what answers hold inside them (`src/autofill/derive.ts`): the city in "Dallas, TX", first and last name from a two-word full name, the full name from the first (and middle) and last name, the ZIP or six-digit PIN code an address or location ends with ("…, OH 43215"), a start date from the notice period in a date box, and the linked job's title for "Position applied for". A location fills without its ZIP code or a note, and only "City, ST" or "City, State, Country" gives a city or a state. A saved answer of the field's own kind comes first, but a screening answer (background check, clearance, travel, commute, former employer…) counts only when both questions ask the same thing: the same stance (willing, have, ever, need), the same numbers and places, and a named company only when it's the job's. Pay goes in only in the unit the field asks for, hourly or yearly: BenchQ never converts (`src/autofill/pay.ts`). Names and contact details under a section about someone else (emergency contact, references, referred by), and a start date in a work-history block, stay with the BDE. Matching reads the question without its examples and notes ("(e.g. LinkedIn)", "(Note: …)"). If the candidate's résumés or the picked one's answers can't load, the panel says so.
- **Panel:** top to bottom: the job card (the job's first letter, title, company, the candidate, and, once the job list has the saved application, its location, pay and when BenchQ found it; pay under 1,000 reads per hour, since the job pool stores no unit), **Autofill**, the run while it goes, a **Resume** and a **Cover letter** section, then **Required**, **Optional** and **Other uploads**. **Mark applied** and **Undo** stay at the bottom. Mark applied steps aside while a run fills the form and is back when it ends, and the panel then scrolls up to **Autofill complete** (or to the run's note when fields are left), stopping just under the sticky top bar, smoothly unless the system asks for reduced motion. The job card keeps to a few short lines: title, company and candidate, location on its own row, pay and when it was found side by side.
- **Never filled:** government, tax and payment IDs, date and place of birth, passwords and account forms, CAPTCHA, consent and legal statements, signatures, uploads other than the picked résumé's file (`src/autofill/never-fill.ts`). A yes or no about having a licence or passport, a profile's user name ("GitHub username"), a name "as on passport", a PIN code and "Tax terms" are questions, so they fill. EEO and self-ID questions fill only from an explicit bank answer, never from a guess. Self-rating questions and experience in a line of work are always left to the BDE.
- **Fill:** every field with an answer, one at a time, each read back after the page updates and again once the run settles. While it runs, the field lists make way for the run: each field joins it as BenchQ reaches it, with a spinner, then a green tick and the value it took, or a warning and why it's the BDE's. The run never waits for the list, and with reduced motion nothing moves. Once it ends, the result note and the lists come back. The note is a small strip: what the run filled ("Filled 15 fields"), then how many fields are still empty, required and optional, and why ("Still empty: 2 required, 1 optional. Autofill didn't recognize these or couldn't fill them. Fill in the required ones below, then submit the form."), counting every empty field on the form; amber while a required field is empty, green otherwise. It goes after six seconds (not while hovered or focused), or with its ✕, and stays when a run stopped because the form changed. Custom dropdowns such as Greenhouse's are opened at fill time, and the answer is matched against the options they show, with one search when it isn't on show; no clear match leaves them untouched, and the row then offers **Choose an option**: the dropdown's options in the panel, and the one picked there is selected on the page. A dropdown or list box that keeps several choices gets each part of the answer, all of them or none. Race and ethnicity lists are read by group, whatever their wording ("East Asian (inclusive of Chinese, …)", "Asian (Not Hispanic or Latino)"; `src/autofill/race.ts`): a broad "Asian" is never narrowed, several saved races pick "Two or More Races" or nothing, and a saved Hispanic answer picks the Hispanic option where the list has one. Work-authorization status sentences ("I am authorized … but will require sponsorship") come from the saved authorization and sponsorship answers, however they're worded (`src/autofill/authorization.ts`), never from a visa type. Styled radios, checkboxes, switches and toggle buttons (`role="radio"`, `aria-pressed`) fill like real ones. A value the form only reformatted, like "11-20-2026" for "11/20/2026", counts as taken. Once the run settles, Autofill fills once more for questions its answers brought out, like "If yes, which visa?". Prior values stay in the page for **Undo**, which puts back every field BenchQ filled, leaves one the BDE has edited, and says which dropdowns couldn't be cleared. A field that can't be filled is put back as it was and stays with the BDE, with the reason on its row. It stays that way when the BDE switches tabs, and a page load offers it again. The extension never submits a form, and **Mark applied** on the linked job, after a confirmation, is the only way it changes status. The confirmation is a modal dialog: it names the job and the candidate, lists the required fields still empty as links back to them (three, then **Show all**), starts on its own **Mark applied**, and Cancel or Esc returns focus to the button. An answer that fits several options, like a saved "Asian" on a form listing East, South and Southeast Asian, stays with the BDE and the row names them: BenchQ doesn't narrow it down. A saved "South Asian" fills that form and any form offering plain "Asian".
- **Tracking:** while the panel is showing, it reads the form every two seconds, because a page has no way to message the extension. A field the BDE fills ticks in the **Required** or **Optional** list and the fills are theirs: Autofill won't write over them. Nor over a value the form held before BenchQ first looked, typed earlier or filled by the site from the résumé: when it differs from the saved answer, **Already on the form** shows both, with **Replace** and **Replace all**. Autofill attaches the picked résumé's file to the form's first résumé upload before anything else, waits for the form to go still (a site such as Lever reads the file and fills fields itself), then fills, BenchQ's answers replacing what the site read. Only an uploaded base's first version has a file (`GET …/resumes/{rid}/file`, `docs/02` §8.2); for any other, the section names the résumé to attach by hand. A file on the form before BenchQ looked stays, and one BenchQ attached is replaced when another résumé is picked, through the page's own remove control when the page shows a taken file as a chip (Greenhouse), and only that file: in the frame that attached it, beside the upload it went to, so a file of the same name the BDE attached elsewhere stays. Every other upload, a cover letter's too, stays with the BDE. The **Resume** section's picker lists this job's tailored résumés, then each base at its newest version, the one in use tagged Active, each with a link to open it in BenchQ, and an older version when it's the one the application names, after its résumé's newest; it starts on the résumé the application names, else this job's tailored one, else the base in use. Picking one fills the form at once when it's the job's form on the page; picking another on a filled form refills BenchQ's own fills from it and takes back those it doesn't answer, never the BDE's. The **Resume** and **Cover letter** sections show whether the form asks for each ("No field found" when it doesn't), tick once a file is attached and show its name, go to the field, and the cover letter one says whether a cover letter is saved for the job. They're found by label (`src/autofill/documents.ts`), since the engine misses résumé uploads; a cover letter can also be a text box. Any other upload is listed last. New fields, removed fields and new dropdown options bring a fresh scan, so there is no Rescan button.
- **`form_data`:** **Mark applied** sends each field's label, value, required flag and source (`autofill` or `bde`) to `applications.form_data` (`docs/02` §9). Values are kept from when they were last seen, across every page of the form, in the panel's memory only and never in Chrome storage, so closing the panel loses them. Passwords, government IDs, payment details, dates and places of birth, signatures, account forms and EEO answers are left out, and an upload is its file name.

### What the picked résumé sends

`GET /api/firms/{firm}/candidates/{cid}/resumes/{rid}?autofill=true` returns the version with its `autofill` list (`docs/02` §8.1): the answers built from the résumé and the entries saved on the version. The extension reads each entry's `question`, `answer`, `key` and `also` and ignores the rest (`src/autofill/resume-answers.ts`).

- An entry with a `key` answers a fixed question: the key finds the form's fields by what they ask, however they're worded (`src/autofill/answer-keys.ts`). A key the backend adds later is matched by its wording until it gets a line there, and `answer-keys.test.ts` fails until it does.
- An entry without a `key` is a question saved on the version, matched by its wording; each of its other wordings (`also`) gets the same answer.
- Answers come typed and are written the way a form takes them: Yes and No, dates as MM/DD/YYYY, the hourly rate as "$85/hr", a notice period as "14 days" or "Immediately", a list on one line. Lists of jobs, schools, projects and awards answer no one field and are left out.
- Whether the candidate may work in the US is worked out from their status, and where they live from the city and state.
- Nothing is stored: the answers and the file stay in the panel's memory while the tab is reviewed.

## Build and setup

- `npm run ext:build` — builds the standalone extension.
- `npm run ext:watch` — rebuilds on source changes.
- `pnpm ext:test` — runs the extension's tests, or in `extension/`: `npm test`, and `npm run test:watch` while working.
- Vite loads `BENCHQ_URL` from `extension/.env`; copy `extension/.env.example` as a starting point. It is the BenchQ web-app origin used for the sign-in tab and all `/api/*` requests. In local development it is `http://localhost:3000`; Next.js rewrites those API paths to the backend at `BACKEND_URL`. For another environment, set it to that BenchQ web-app origin, rebuild, and ensure the backend `ALLOWED_ORIGINS` includes the extension's exact `chrome-extension://` origin.
- **Site access (the manifest is built, not hand-written):** `extension/manifest.base.json` holds the fixed parts and
  `extension/hosts.json` the job boards and application systems BenchQ may read without asking. `npm run build` writes
  `dist/manifest.json` from them plus `BENCHQ_URL`: `host_permissions` is BenchQ's address and those sites only, and every
  other https site is `optional_host_permissions`. For an employer's own careers page the panel says why it needs access
  (`SiteAccessNotice`), then Chrome asks once, from the BDE's click on Allow. Only the tab's own site is asked about, so
  a form framed from an unlisted domain is "unreadable" like any frame BenchQ can't reach. A store build is
  `npm run build:store` (`ext:build:store` from the root is not added): it reads `extension/.env.store`, which holds the live
  address `https://www.benchq.io`, and fails on a local address or all-sites access.
- **Publishing:** `.github/workflows/extension-publish.yml` runs only when a push to `main` changes `extension/**` (or by
  hand), never for backend or frontend changes. It tests, runs `build:store`, stamps the version as `major.minor.<run number>`
  (the store refuses a version it already has), zips, and uploads and submits through the Chrome Web Store API when the
  secrets `CHROME_EXTENSION_ID`, `CHROME_CLIENT_ID`, `CHROME_CLIENT_SECRET` and `CHROME_REFRESH_TOKEN` exist. Without them
  it only keeps the zip. The first upload and the listing are done by hand in the store dashboard.
- Load unpacked in Chrome: run the build, open `chrome://extensions`, enable Developer mode, select **Load unpacked**, and choose `extension/dist/`.

The extension calls the BenchQ origin directly with browser-managed cookies. Backend CORS and unsafe-request origin checks use `ALLOWED_ORIGINS`; the deployment must include the installed extension's `chrome-extension://<extension-id>` origin. This is an environment setup dependency, not changed by this implementation. The manifest's HTTPS host access is also what lets the page script run on employer sites, in connected tabs only; API calls stay limited to the configured `BENCHQ_URL`.

## Verification and limitations

- **Build:** `npm run ext:build` completed successfully. The load-unpacked extension is in `extension/dist/`.
- **API and local test data:** 10 jobs from `src/mocks/data/jobs.json` are linked to five candidates in the same firm: three candidates assigned to Adnan Khan and two assigned to Sneha Rao. Each has two saved jobs. The APIs returned six saved jobs for Adnan before applying one; `PATCH .../candidate-status` returned `applied` at revision 1; subsequent reads returned five saved plus one applied for Adnan and four saved for Sneha. The applied item remains visible with a disabled action. The BDE candidate filter was confirmed by the API results.
- **Runtime:** the side panel was not exercised in Chrome; load unpacked from `extension/dist/`. The extension uses the configured `BENCHQ_URL`, and the backend must allow the extension origin in `ALLOWED_ORIGINS`.
- **CORS:** runtime calls will fail unless the deployment allowlists the extension origin as described above. Backend CORS configuration was intentionally not modified.
- **Chrome packaging:** Vite output is load-unpacked output; no store package or signing was produced.
